# 密钥交接说明

本文用于服务器部署交接，说明哪些密钥需要提供给负责人，以及每个密钥的重要性。

## 一、交接原则

1. 真实密钥不要写进仓库。
2. 同一套数据库迁移到新机器后，涉及加密和登录的密钥必须保持一致。
3. 只给需要部署的人，不要公开分发。
4. 若密钥发生变化，要先确认是否会影响已登录状态、已保存 API Key 和已有数据。

## 二、必须交接的内容

| 名称 | 重要性 | 作用 | 是否可随意更换 |
| --- | --- | --- | --- |
| `FAMAS_SECRET_KEY` | 最高 | 登录 token 签名、部分安全逻辑、API Key 保护相关 | 不可随意更换 |
| `FAMAS_SECRET_ENCRYPTION_KEY` | 最高 | 后端保存的 API Key 加密解密 | 不可随意更换 |
| `FAMAS_DATABASE_URL` | 最高 | 指向实际使用的数据库 | 部署时必须正确配置 |
| `FAMAS_ADMIN_PASSWORD` | 高 | 首次初始化管理员账号时使用 | 仅在初始化阶段需要 |
| 模型 API Key | 高 | 供问答、schema、KG 抽取等调用外部模型 | 视供应商策略决定 |

## 三、每个密钥的重要性

### `FAMAS_SECRET_KEY`

重要性：**最高**

原因：

- 登录后的 token 依赖它签名。
- 用户已保存的登录状态可能依赖它。
- 同一套数据库切换机器后，若它变化，旧登录态可能失效。
- 对已有数据的访问安全相关。

建议：

- 迁移到服务器时必须与原环境保持一致。
- 不建议频繁修改。

### `FAMAS_SECRET_ENCRYPTION_KEY`

重要性：**最高**

原因：

- 用于加密保存模型 API Key。
- 如果它变化，历史已保存的 API Key 可能无法解密。
- 会直接影响问答、图谱、schema 等依赖模型调用的功能。

建议：

- 迁移到服务器时必须与原环境保持一致。
- 更换前必须先准备重新录入所有 API Key。

### `FAMAS_DATABASE_URL`

重要性：**最高**

原因：

- 决定项目到底连哪一个数据库。
- 服务器部署时如果写错，可能会连错库或直接无法启动。

建议：

- 正式环境优先使用独立数据库实例。
- 部署前先确认备份和迁移流程。

### `FAMAS_ADMIN_PASSWORD`

重要性：**高**

原因：

- 用于首次创建管理员账号。
- 如果数据库里已经有管理员账号，通常不需要再次提供。

建议：

- 只在首次初始化或重建管理员账号时交接。
- 不要把它当作长期固定公开密码。

### 模型 API Key

重要性：**高**

原因：

- 直接影响问答、schema 生成、KG 抽取、图像处理等功能是否能跑。
- 没有它，项目可能只能打开页面，核心能力不可用。

建议：

- 单独安全交接。
- 如果负责人只负责部署而不负责日常模型费用，最好单独保存来源和用途。

## 四、不要交接的内容

- `dev-secret`
- 临时公网测试密钥
- Cloudflare 临时地址
- 任何写进本地 `docs/` 的临时记录
- 真实 API Key 明文留在仓库里

## 五、交接后检查

交接完应确认：

1. 负责人已拿到正确的 `FAMAS_SECRET_KEY`。
2. 负责人已拿到正确的 `FAMAS_SECRET_ENCRYPTION_KEY`。
3. 负责人知道数据库指向哪里。
4. 负责人知道管理员密码是否只是首次初始化用。
5. 负责人知道哪些模型 Key 对应哪些功能。

## 六、最简交接建议

如果只想发最必要的信息，可以只给：

- `FAMAS_SECRET_KEY`
- `FAMAS_SECRET_ENCRYPTION_KEY`
- `FAMAS_DATABASE_URL`
- 模型 API Key
- `FAMAS_ADMIN_PASSWORD`（仅首次初始化时）
